# Lookup and decoder optimization pass

Baseline: `cf5b672`. Measured on Linux/arm64, Neoverse N2, Go 1.27.1.
These are local before/after comparisons, separate from the CI-generated
architecture tables. No amd64 performance claim is made.

## Implementation

- `GetMany` returns immediately for an empty query set.
- For 32–256 queries on a record at least four bytes per requested key,
  `GetMany` uses 64 bucket heads and 256 links stored on the stack. The index
  is built only after a field passes the existing key-length filter. Settled
  slots leave their chains; provisional empty values remain. Reverse insertion
  preserves the existing duplicate-query ordering. Full key comparisons still
  establish matches. Small sets, very short records, and sets above 256 keys
  retain linear matching.
- `AppendUnescape` handles its first search and literal prefix before the
  decode loop. Adjacent escapes skip both the word probe and the empty copy.
  Ordinary Unicode escapes decode inline; surrogate combination is a separate
  slow path that receives the already parsed first code unit.
- A destination with zero capacity reserves the raw input length once when an
  escape is present. Existing buffers retain normal append growth and can still
  decode without allocation when they fit only the shorter decoded output.

The raw-length reservation trades retained capacity for fewer allocations:
escape-heavy output can be substantially shorter than its buffer capacity.
The benchmark reports both allocated bytes and allocation counts; fewer
allocations do not imply fewer retained bytes for every input.

## Measurement

Both binaries use the same tests and toolchain. The A/A control (six alternating
100 ms rounds) was statistically unchanged on every measured row. A linked but
unexecuted padding test shifted the two-key lookup by 0.8%, with the other
calibration rows statistically unchanged. Small movements should be interpreted
against that layout sensitivity and the existing notes in `CLAUDE.md`.

Final comparisons use six alternating rounds, pinned to CPU 1, with no builds,
fuzzers or other benchmark series running concurrently. Root benchmarks use
one second per measurement. The comparison-module check also includes unchanged
third-party parsers as controls.

Build a baseline binary with the new benchmark files as well as the original
implementation, and a candidate binary with the same benchmark files. From the
root module, run:

```sh
python3 bench/compare.py /tmp/before.test /tmp/after.test \
  --cpu 1 --output /tmp/logfmt-comparison \
  --bench 'Benchmark_(GetManyScale|GetManyShapes)$' --benchtime 1s
```

The harness writes raw `before.txt` and `after.txt` files and runs `benchstat`.
Use the same binary in both positions for an A/A control. For the separate
comparison module, build its binaries separately and pass `--cwd bench`.

## Validation

- Go 1.21.13 compatibility tests and Go 1.27.1 tests.
- Race tests; root statement coverage 99.8%. The remaining uncovered statement
  is the pre-existing defensive timestamp parse guard.
- Tests and `go vet` in both modules; `golangci-lint` reports zero issues in both.
- Differential fuzzing: parser 20 s, existing lookup reference 20 s, indexed
  lookup including duplicate query slots 30 s, decoder 30 s.
- amd64 cross-compilation. Only arm64 performance was measured.
- Allocation, source aliasing, empty/absent, duplicate-slot ordering, malformed
  prefix, index boundary, collision, and exact-capacity decoder regression tests.

## Experiments excluded

- A bitmap index at eight queries regressed the small-query benchmark. The
  final crossover is deliberately higher.
- Converting byte keys to strings for a fingerprint copied short keys and
  allocated for long keys. A generic helper accepts both input types directly.
- Eager index construction lost heavily when every field failed the length
  filter. Lazy construction preserves that inexpensive rejection path.
- Moving index dispatch after the small-path setup increased its per-slot
  cost. Dispatch stays before that setup.

## Lookup results

Medians from the final six-round, one-second series. All rows below use a
reusable result buffer and remain at **0 B/op, 0 allocs/op**.

| Benchmark | Before | After | Time change |
|---|---:|---:|---:|
| Empty query list on sample line | 311.9 ns | 3.239 ns | −99.0% |
| 32 ordered queries (`GetManyScale`) | 657.8 ns | 539.6 ns | −18.0% |
| 64 ordered queries (`GetManyScale`) | 1.901 µs | 1.050 µs | −44.8% |
| 128 ordered queries (`GetManyScale`) | 6.211 µs | 2.078 µs | −66.5% |
| 64 queries, reverse order | 6.938 µs | 1.096 µs | −84.2% |
| 64 queries, reverse order with common suffix | 6.982 µs | 2.300 µs | −67.1% |
| 256 ordered queries | 22.744 µs | 3.975 µs | −82.5% |
| 256 queries, reverse order | 91.945 µs | 6.474 µs | −93.0% |
| 256 absent queries with matching key lengths | 174.430 µs | 6.603 µs | −96.2% |
| 64 absent queries rejected by key length | 487.9 ns | 523.9 ns | **+7.4%** |
| 256 absent queries rejected by key length | 1.906 µs | 2.025 µs | **+6.2%** |
| One requested key (`GetManyScale`) | 17.27 ns | 17.55 ns | **+1.6%** |

The all-length-mismatch regression remains after avoiding index construction:
the indexed callback carries additional state and dispatch overhead. Its cheap
rejection path costs a little more even when the chains are never built.
Index setup can also dominate records with few potential matches; the record
length gate is a heuristic, not a guarantee of a particular field count.

The four existing core measurements remain effectively unchanged:
`IterateOur` 299.2 → 299.5 ns (statistically unchanged),
`DecodeKeyval_Custom` 595.7 → 595.5 µs (statistically unchanged),
`GetMany_TimestampLevel` 66.13 → 65.92 ns, and
`LevelTS_LogFmt` 58.70 → 58.84 ns. The latter two movements are below 0.4%
and below the layout control's observed lookup shift. The 16-query and
short-record shapes likewise show no substantial change.

## Decoder results

Medians from the final six-round, one-second series. Reused buffers remain at
**0 B/op, 0 allocs/op**.

| Benchmark | Before | After | Time change |
|---|---:|---:|---:|
| 500 escaped quotes in 1 KB, reused buffer | 2.992 µs | 1.020 µs | −65.9% |
| Adjacent newline escapes, reused buffer | 2.8765 µs | 805.4 ns | −72.0% |
| Adjacent newline escapes, fresh buffer | 3.354 µs | 1.058 µs | −68.5% |
| JSON-containing buffer, fresh destination | 380.7 ns | 261.5 ns | −31.3% |
| Unicode controls, fresh destination | 193.0 ns | 109.8 ns | −43.1% |
| Surrogate pairs, reused buffer | 230.8 ns | 179.0 ns | −22.4% |
| Malformed escapes, reused buffer | 280.8 ns | 247.8 ns | −11.8% |
| `UnescapeUnicode` | 80.72 ns | 75.55 ns | −6.4% |
| `AppendValueUnicode` | 114.0 ns | 109.8 ns | −3.7% |
| Clean 1 KB, reused buffer | 49.74 ns | 48.23 ns | −3.0% |
| Existing prose `Unescape` benchmark | 25.10 ns | 25.71 ns | **+2.4%** |

The adjacent-escape branch earns its cost when escapes touch. Most sparse
escape-gap rows remain within roughly 1.5%; they do not receive the dense
speedup. The 40-byte-gap row showed a 7% excursion in early rounds, but the
completed series was statistically unchanged (358.0 → 357.8 ns, p=0.660).
The realistic reused JSON-message benchmark is effectively flat
(188.2 → 187.3 ns); the significant JSON gain is for fresh destinations.

Fresh-buffer allocation counts and total allocated bytes:

| Payload | Allocations before → after | B/op before → after |
|---|---:|---:|
| JSON-containing buffer | 4 → 1 | 720 → 288 |
| Adjacent newline escapes | 7 → 1 | 1016 → 1024 |
| Unicode controls | 4 → 1 | 240 → 128 |
| Surrogate pairs | 4 → 1 | **120 → 192** |
| Malformed escapes | 6 → 1 | 504 → 160 |
| Clean 1 KB | 1 → 1 | 1024 → 1024 |

In particular, surrogate-heavy input allocates 60% more total bytes despite
using fewer allocations. Passing a reusable destination sized to the decoded
output avoids the raw-length reservation; the regression test pins that case.

## Comparison-module check

Six alternating 200 ms rounds in the separate `bench/` module measured:

| Benchmark | Before | After |
|---|---:|---:|
| `ParseAll_Big_Mine` | 300.1 ns | 300.4 ns (unchanged) |
| `ParseAll_Typical_Mine` | 64.56 ns | 64.65 ns (unchanged) |
| `ParseEscaped_Mine` | 188.7 ns | 176.7 ns (−6.4%) |
| `Extract_Mine` | 65.97 ns | 65.51 ns (−0.7%) |

All four remain allocation-free. Treat these as secondary evidence: some
unchanged third-party rows moved between −1.4% and +3.0%, showing that small
cross-binary differences cannot be attributed to this implementation. The
primary claims above use the root suite, its A/A control, and its layout
calibration; no cross-library relative-speed claim is inferred from this check.
